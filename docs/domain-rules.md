# Domain rules

## Members

- IDs and UTC audit timestamps are generated by services; callers cannot overwrite them.
- Names are trimmed and contain 1–200 characters. Duplicate display names are allowed; IDs distinguish people.
- Birth dates may be unknown and cannot be after the current UTC date. There is no arbitrary minimum parental age.
- Gender: Male/Female. Life status: Living/Deceased. Marital status: Single/Married/Divorced.
- Marital status may be entered independently if the related person is not recorded. An active recorded spouse requires Married.
- Editing gender revalidates existing parent limits. Death does not automatically remove relationships or change marital state.
- Deletion is blocked until all attached relationships have been explicitly removed; SQL foreign keys also enforce this.

## Relationships

- `Parent` means source is parent of target. `Son`/`Daughter` input reverses endpoints after validating the source's gender.
- `Spouse` and `FormerSpouse` are symmetric, with exactly one normalized row per pair. Current and former states cannot coexist for the same pair.
- Labels describe the named person's gender; there is no opposite-gender marriage requirement.
- Self-links, missing endpoints, unsupported/inactive types, and duplicate facts are rejected.
- Each child may have at most one male and one female parent. Parents may have multiple children.
- Ancestry must be acyclic. Current/former spouse pairs may not be ancestors/descendants; adding a parent link rechecks all spouse facts for this contradiction.
- A member may have at most one active spouse and any number of distinct former spouses.
- Siblings share at least one parent; half-siblings are included, the selected member is excluded, and results are deduplicated.
- Validation failures have stable codes, field names, and human-readable messages. The UI displays the messages without exposing SQL to ViewModels.

## Atomic marital-state changes

| Operation | Result for both affected members |
| --- | --- |
| Add current spouse | Married |
| Mark current spouse as former | Divorced, preserving the same relationship ID and creation timestamp |
| Add historical former spouse | Married if another active spouse exists, otherwise Divorced |
| Remove incorrect spouse fact | Married if an active spouse remains; otherwise Divorced if former-spouse links remain; otherwise Single |

Parent changes do not alter marital statuses. Corrections to spouse facts recalculate affected statuses even if those statuses were previously entered manually. Every link mutation and its status updates either commit together or roll back together.

## MVP boundaries

The binary parent model and single active spouse policy are deliberate defaults from the approved proposal. Adoptive/step/social parent categories, marriage episodes and dates, same-pair remarriage history, widowed status, cousins/in-laws, shared multi-user hosting, import/export, and a graphical tree canvas are not implemented. The current UI provides member details and direct/derived relationship lists. Adding a row to `RelationshipType` does not add executable behavior; new kinds need deliberate code and schema changes.
